# PR Writer

**TL;DR:** A fork-aware skill that creates pull requests from approved modernization plans. It builds a branch on the user's fork, pushes file changes, and opens a PR against the upstream base branch — with structured sections for changes, artifacts, risk items, and recommendations. Supports dry-run mode for preview without side effects.

## Overview

After the Implementation Agent completes code changes for a task, the PR Writer packages those changes into a GitHub pull request. All Git operations target the **fork** (`{forkOwner}/{repoName}`), never the upstream repository, ensuring the upstream remains clean until the PR is reviewed and merged.

## Workflow

```
  Implementation Agent
         │
         ▼
  ┌──────────────┐     ┌──────────────┐     ┌───────────────────┐
  │ Build branch │────▶│ Push files   │────▶│ Create PR         │
  │ on fork      │     │ to branch    │     │ fork → upstream   │
  └──────────────┘     └──────────────┘     └───────────────────┘
         │                    │                       │
   jurassic/task-{id}   FileChange[]          {forkOwner}:{branch}
                                                → {baseBranch}
```

### Step 1 — Create Branch

A new branch is created on the fork from the target `baseBranch`:

- **Branch name:** `jurassic/task-{taskId}`
- The `taskId` is sanitized: non-alphanumeric characters (except `_`, `/`, `-`) are replaced with `-`, consecutive dashes are collapsed, and leading/trailing dashes are trimmed.

### Step 2 — Push Files

All `FileChange` entries are pushed to the branch on the fork. Each entry specifies:

| Field | Type | Description |
|-------|------|-------------|
| `path` | `string` | File path relative to repo root |
| `content` | `string` | New file content |
| `changeType` | `"create" \| "modify" \| "delete"` | Type of change |

### Step 3 — Create Pull Request

A pull request is opened from `{forkOwner}:{branchName}` to the upstream `{baseBranch}`:

- **Title:** `[Jurassic] {taskDescription}`
- **Body:** structured markdown (see below)

## PR Body Template

The generated PR body contains up to four sections plus a footer:

```markdown
## Changes

{taskDescription}

- `src/auth/login.ts` (modify)
- `src/auth/types.ts` (create)

## Artifacts Referenced

- `artifact-dep-graph-001`
- `artifact-risk-scores-001`

## Risk Items

| ID | Severity | Description |
| --- | --- | --- |
| R-01 | high | Auth token rotation not covered by tests |
| R-02 | medium | Legacy session middleware depends on removed export |

## Recommendations

- Add integration tests for token refresh flow
- Verify session middleware after dependency swap

---
*Generated by Jurassic Modernization Agent*
```

Sections are omitted when their data is not provided (e.g., no `artifactIds` → no "Artifacts Referenced" section). An empty `fileChanges` array produces the placeholder `_No file changes._`.

## Dry-Run Mode

When `dryRun: true` is set in the input:

- The branch name, title, and body are computed normally.
- **No GitHub API calls are made** — no branch, no push, no PR.
- The output `status` is `"dry-run"` instead of `"created"`.
- Useful for previewing PR content during development or testing.

## Fork Safety

The PR Writer enforces fork-awareness at every step:

1. `createBranch` targets `{forkOwner}/{repoName}`.
2. `pushFiles` targets `{forkOwner}/{repoName}`.
3. `createPullRequest` sets `head` to `{forkOwner}:{branchName}`, ensuring the PR originates from the fork.

This guarantees the upstream repository is never written to directly.

## Input Validation

The skill validates all required fields before proceeding:

| Field | Required | Validation |
|-------|----------|------------|
| `forkOwner` | Yes | Non-empty string |
| `repoName` | Yes | Non-empty string |
| `taskId` | Yes | Non-empty string |
| `taskDescription` | Yes | Non-empty string |
| `fileChanges` | Yes | Must be an array |
| `baseBranch` | Yes | Used as PR target |
| `dryRun` | No | Defaults to `false` |
| `artifactIds` | No | Optional string array |
| `riskItems` | No | Optional array of `{id, severity, description}` |
| `recommendations` | No | Optional string array |

Validation failures throw immediately with a descriptive error message.

## Error Handling

If any GitHub API call fails during the create → push → PR sequence:

- The error is caught and the output `status` is set to `"failed"`.
- The `error` field contains the error message.
- The computed `branchName`, `title`, `body`, and `fileCount` are still returned for diagnostics.

## Integration with Incremental PR

For large modernization plans that span multiple tasks, each task produces its own PR via the PR Writer. The `incremental_pr` skill coordinates sequencing — the PR Writer is the leaf operation that creates each individual pull request.
